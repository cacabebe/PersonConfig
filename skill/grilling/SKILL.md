# 深度追问

围绕主题的每个方面毫不留情地追问用户，直到达成共同理解。将计划视为决策树：每个决定都可能解锁、限制或改变后续决定。按依赖顺序走完每个分支，并为每个问题给出推荐答案。

提问节奏由下文的“按决策前沿提问”规则决定。唯一无需用户回答的例外是符合下文规则、可由 Agent 暂定回答的问题。

如果某个事实能通过检查环境、文件系统或可用工具获取，就主动查找，不要询问用户。决定权属于用户：所有重要的、取决于个人偏好的或难以撤销的决定，都必须交给用户并等待回答。

在用户确认已经达成共同理解之前，不要实施讨论中的方案。

## 创建讨论记录

在提出第一个问题之前：

1. 创建一个新的讨论记录文件。不得要求固定路径或文件名。尊重用户指定的位置或名称，不得覆盖已有文件。
2. 记录主题、创建时间、当前目标以及以下状态含义：
   - `用户已确认`：用户已经明确回答或批准。
   - `Agent 暂定（待复审）`：Agent 未询问用户便自行选择的暂定答案。
3. 告知用户讨论记录文件创建在何处。

创建和更新讨论记录属于访谈过程，不算实施讨论中的方案。

## 按决策前沿提问

`当前决策前沿`是指所有前置决定都已解决、因此现在可以回答的未决问题。每轮开始时，重新计算当前决策前沿；不得把仍依赖于未决答案的问题提前放进本轮。

默认每轮提出 1 到 3 个互不依赖的问题。只有当同一批问题的答案互不改变对方的含义、选项或推荐答案时，才可以合并提问。用户可以按编号一次回答多个问题。

以下情况必须拆成一次只问一个问题：

- 问题重要、取决于个人偏好、难以撤销，或会实质影响范围、成本、安全、隐私、外部系统或其他人；
- 任一答案可能改变另一问题的含义、可选项、推荐答案或后续优先级；
- 用户明确要求一次只讨论一个问题。

用户尚未回答本轮的全部问题时，将未答问题保留在当前轮；不要借此提前提出新的下游问题。每轮获得的回答会重新塑造决策树，写入已确定的决定后再计算下一轮前沿。

批量提问时使用以下结构：

```markdown
本轮问题（可按编号分别回答）：

❓ **Q<n> - <问题标题>**
问题：...
➡️ 推荐答案：...
理由：...
```

理由保持简短。不要用没有关联关系的一长串问题压倒用户，也不要把多个实际互相依赖的问题伪装成独立问题。

## 保留用户决定权

当一个决定重要、取决于个人偏好、难以撤销，或会实质影响范围、成本、安全、隐私、外部系统或其他人时，必须询问用户。给出推荐答案及简要理由，然后等待相应回答。除当前小批量中的其他独立问题外，不要在用户回答前继续推进。

满足以下任一条件时，可以由 Agent 自行回答而不打断用户：

- 答案影响较小且容易修改；或
- 根据现有上下文，用户大概率会接受推荐答案。

不得仅因推荐答案看起来显而易见，就自行决定重要或难以撤销的问题。如果无法判断影响大小，必须询问用户。

对于由 Agent 自行回答的问题：

1. 明确写出问题和推荐答案。
2. 将推荐答案作为当前采用的答案。
3. 立即写入讨论记录，状态标记为 `Agent 暂定（待复审）`，并说明为何可以推迟向用户确认。
4. 重新计算决策前沿，继续访谈。

## 立即记录每个结论

任何问题一旦确定答案，必须先把它写入讨论记录，再进入下一个分支或下一轮。不要等到一整轮结束才批量补写。使用以下结构：

```markdown
## D<n>：<简短的决定标题>

- 关联问题：Q<n>
- 问题：...
- 推荐答案：...
- 决定：...
- 状态：用户已确认 | Agent 暂定（待复审）
- 前置决定或依赖：...
- 理由：...
- 假设或待跟进项：...
```

不得把尚未落盘的决定积压在记忆中。如果用户修改了决定，更新原条目中的最终决定，并保留简短的修订说明，避免出现相互冲突的结论。

## 完成与复审

只有当决策前沿为空、每个分支都已访问且没有重要的隐含假设时，才结束访谈。此时：

1. 汇总用户已确认和 Agent 暂定的决定数量。
2. 总结已确定的方向、接受的取舍、明确不做的事项，以及仍开放的问题。
3. 指出讨论记录文件的位置，并明确说明暂定条目仍需复审。
4. 用户要求复审时，与用户共同检查暂定条目；每次只处理一个有实质分歧的问题。用户接受后，把状态改为 `用户已确认`；用户否决时，更新决定并记录修订说明。
5. 仍有重要问题未解决时，不得声称已经达成共同理解。
6. 在用户确认共同理解已经完整之前，不得实施方案。
