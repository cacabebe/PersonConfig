# 困难问题复盘

用可复现证据解释问题为何发生、此前为何没有解决，以及如何用最小且可执行的工程措施防止复发。

## 边界

- 默认只分析和报告，不修改代码、规范、契约或测试；用户同时授权修复时，复盘完成后再按项目规则实施。
- 完整阅读根目录及受影响工程的 `AGENTS.md`、相关现行专题规范、功能契约和当前有效 ADR。Skill 不得覆盖这些规则。
- 将聊天中的推测和失败尝试视为线索；只有仓库、日志、测试或可复现行为支持的内容才能标为已确认根因。
- 问题尚未复现或证据不足时，输出领先假设和缺失证据，不得伪造确定结论。

## 工作流

1. **收集证据**
   - 明确预期行为、实际行为、复现条件、受影响范围和当前状态。
   - 检查相关差异、失败命令与日志、测试、契约、规范、ADR 和近期相关改动。
   - 区分已经证实的事实、尚待验证的假设和缺失输入。

2. **定位根因**
   - 沿真实调用链、数据流或构建链追到最早违反预期的位置，不停留在表面症状。
   - 使用最贴切的分类：规范缺失、契约违反、变更传播遗漏、测试缺口、隐含假设、环境或工具链问题；必要时说明多个因素的因果顺序。
   - 给出支持结论的文件、行、命令输出或复现证据。

3. **解释失败尝试**
   - 逐项说明此前方案针对了哪个假设、为何未触及根因或为何引入新的失败。
   - 不因结果失败就否定当时合理的证据；指出缺失的检查、错误边界或判断跳跃。

4. **检查同类风险**
   - 使用定向搜索检查同一入口、调用方、实现模式、契约字段或配置是否存在相同风险。
   - 只扩展到证据支持的范围；不要把复盘变成无边界的全仓审计。

5. **设计预防措施**
   - 优先修正根因并利用现有类型、Schema、数据库约束、静态检查、架构测试或行为测试。
   - 只有机器门禁无法表达稳定规则时才建议文档或检查清单；不得为一次性问题新增抽象、依赖或流程。
   - 将措施分为必须实施和候选增强，并写明各自阻止的具体失败。

6. **路由知识沉淀**
   - 按根目录 `AGENTS.md` 分类：任务局部事实留在计划或验证记录；已确认稳定规则进入唯一现行专题规范；满足标准的已确认决策进入 ADR；未确认事项保留为待决项；没有稳定新知识时明确说明无需沉淀。
   - 未经项目负责人确认，不得把业务语义、安全权限、外部契约或难以回滚的选择提升为现行规则。

## 输出

使用以下结构，省略没有事实内容的章节：

- **结论**：根因状态、影响和最高优先级措施。
- **证据**：复现、文件位置、命令或测试结果。
- **失败尝试**：此前方案及其失效原因。
- **同类风险**：已检查范围和发现。
- **预防措施**：必须实施项、候选增强及对应失败。
- **知识沉淀**：目标位置、待确认事项或“无需沉淀”。
- **未验证项**：缺失环境、输入和后续验证方式。
